Software setup

Concentration-response modelling with bayesnec — SETAC Australasia 2026

Published

September 19, 2026

ImportantComplete this before the workshop

This setup takes most people between thirty minutes and two hours, and some of it cannot be hurried: package installation and the CmdStan build both take time that depends on your machine and your network.

There is no time set aside during the workshop to install or repair software. If you arrive without a working installation you will be able to watch, but you will not be able to fit models alongside the demonstrations, and most of the day is spent fitting models.

Work through this document, then run the verification check in the final section. Do it early, so that a problem has time to be resolved before the day.

Software required

Software Purpose
R the language everything else runs in
A C++ toolchain compiles each Bayesian model before it is fitted
CmdStan the sampler that fits the models
Positron the editor used throughout the workshop
Git retrieves the workshop materials

The C++ toolchain is the part that differs by operating system, and it is the part that fails most often. On Windows it is Rtools, on macOS the Xcode Command Line Tools, and on Linux the standard build tools.

Bayesian model fitting works differently from most R modelling. Each model is translated into C++, compiled into a program, and run. That is why a compiler is needed at all, and why the first fit of a session takes longer than later ones.

Route by operating system

Windows is the tested and recommended route, and it is the one described in most detail below. The difficulties Stan had on Windows historically came from an older interface, rstan, which required matched versions of several compiled packages. The current interface, cmdstanr, avoids most of that.

Linux is also tested. macOS is not, because the workshop organisers have no Mac available. Mac users should follow the outline in the macOS section, which points to the authoritative upstream instructions, and then run the same verification check as everyone else. The check is what determines whether you are ready, not which instructions you followed.

The Windows Subsystem for Linux is a fallback for one situation only, where compilation on Windows is blocked by security policy on a machine you cannot change. It is not a simpler route: it means a second installation of R, a second package library and a different way of referring to your files. Do not start there.

Windows

R and Rtools

Install R first, then Rtools.

Download R from CRAN and install whichever version CRAN currently offers — do not go looking for an older one. This document was written against R 4.5.x, and has since been re-verified against R 4.6.1 (see the Linux section below); either is fine. What matters is that Rtools matches the R you install, not which minor version that is.

Then install the matching Rtools, from CRAN’s Rtools page. CRAN’s own page names it inconsistently — you may see “Rtools45”, “RTools 4.5” or “Rtools for R 4.5.x” — these all mean the same installer. Rtools version numbers do not track R’s one-for-one: Rtools 4.5 is current for every R version from 4.5.0 onward, including R 4.6.x, so do not go looking for a separate “Rtools 4.6” — there is not one as of this writing. Check CRAN’s Rtools page for the current mapping, since this changes as new R and Rtools versions are released. Accept the default installation location.

WarningRtools must match your version of R

An Rtools built for an earlier R than the one you installed is the most common single cause of setup failure, and the error it produces does not mention version numbers. Check CRAN’s Rtools page for which Rtools release currently covers your R version — do not assume the two version numbers must match exactly, since one Rtools release can cover several R releases.

Positron

Download and install Positron. It will find your R installation automatically. If you installed R after Positron, restart Positron so that it detects it.

Git

Install Git for Windows, accepting the defaults. Git is used to retrieve the workshop materials, as described in the workshop materials section below.

R packages

Open Positron and run the following in the R console.

cmdstanr is not on CRAN, so it comes from the Stan project’s own repository:

install.packages("cmdstanr",
                 repos = c("https://stan-dev.r-universe.dev",
                           getOption("repos")))

Then the rest:

install.packages(c("brms", "posterior", "bayesplot",
                   "ggplot2", "dplyr", "tidyr", "drc"))
Noterstan is a dependency, not a step

brms installs rstan as a dependency. That is expected: rstan must be installed, but the workshop does not use it as the sampler, so it does not matter if you never call it directly. No further action is needed here — the next step is bayesnec, below.

bayesnec is installed from the development branch, which contains changes not yet released to CRAN and is what the course material is built against. This needs the remotes package first — install it if you have not already:

install.packages("remotes")

Then install bayesnec itself:

remotes::install_github("open-AIMS/bayesnec", ref = "dev")

If you paste this last command in before installing remotes, R replies that it could not find the function install_github (or that there is no package called remotes). That is not a sign anything is broken — install remotes with the command above and then re-run this one.

NoteEstimates may differ slightly from the course pages

dev changes as the package is developed, so a fit made now will not always reproduce the numbers printed on the course pages to the last decimal place. Estimates should agree to well within the width of their credible intervals. A difference larger than that is worth raising rather than accepting.

CmdStan

First confirm the compiler is configured. On a current Rtools this passes without doing anything; fix = TRUE repairs the problems it can rather than only reporting them:

cmdstanr::check_cmdstan_toolchain(fix = TRUE)

Then install CmdStan. Three things need setting, and all three have been observed to stop a fresh installation:

dir.create("C:/cmdstan")           # cmdstanr will not create it
options(timeout = 1800)            # the default of 60 seconds is far too short
cmdstanr::install_cmdstan(dir = "C:/cmdstan")

The directory must exist first. install_cmdstan() does not create it, and stops with Assertion on 'dir' failed: Directory 'C:/cmdstan' does not exist.

The download needs a longer timeout. The CmdStan archive is about 49 MB, and R’s default options(timeout) is 60 seconds, which is not enough on any ordinary connection. The timeout argument of install_cmdstan() does not govern the download — the option does. Measured on a connection delivering about 500 KB/s: the download failed with Download of CmdStan failed with error at the default, and completed in 4.9 minutes at timeout = 1800 with nothing else changed. Conference and hotel networks are commonly slower than that, so set it.

The default location is inside your home directory. On many Windows machines, particularly work-managed ones, that directory is synchronised by OneDrive, and the CmdStan build fails there. The same failure occurs when the path contains a space or a character outside the standard English alphabet, which happens when a Windows username does. Installing to C:/cmdstan avoids all three, and costs nothing if none of them applies to you.

Because that is not the default location, tell R where to find it in every future session. Run usethis::edit_r_profile(), or open .Rprofile in your home directory, and add the line below, replacing the version number with the one you installed:

options(cmdstanr_cmdstan_path = "C:/cmdstan/cmdstan-2.39.0")

Without this, every new session reports that CmdStan is not installed.

Recurring problems on Windows

install_cmdstan() fails. Run it again with these arguments:

cmdstanr::install_cmdstan(overwrite = TRUE, quiet = FALSE, dir = "C:/cmdstan")

This is the failure most recently observed on a fresh Windows machine, and this is what resolved it. overwrite = TRUE is the part that matters. A first attempt that fails partway through the build leaves a partly built directory behind, and a second attempt without overwrite declines to replace it, which produces an error resembling the original one. quiet = FALSE only prints more of the build output, which is worth having because the default output is truncated and does not identify which stage failed.

A model compiles but no chains run. cmdstanr reports “No chains finished successfully”, which names neither a cause nor a file. The usual reason is that Rtools changed after CmdStan was installed. CmdStan builds its own tbb.dll, linked against the toolchain that built it, so a CmdStan built under Rtools44 requires libraries that Rtools45 does not provide; the model still compiles and then every chain exits immediately with STATUS_DLL_NOT_FOUND. Rebuild CmdStan:

cmdstanr::install_cmdstan(overwrite = TRUE, dir = "C:/cmdstan")

Anyone who upgrades R and Rtools between installing CmdStan and the workshop will meet this.

Rtools is installed but cmdstanr cannot find it. cmdstanr chooses which Rtools to look for from your R version, and the mapping changed between releases. Version 0.9.0 sends R 4.5.x to Rtools45; 0.8.0 sent every R from 4.4 onward to Rtools44. With an older cmdstanr and the Rtools45 this document specifies, it searches for a toolchain you were never asked to install and reports it missing. Install cmdstanr 0.9.0 or later, which is what the r-universe repository above supplies. check_setup.R reports the version.

Compiling is very slow. Windows Defender inspects each newly compiled program. A compile that should take under a minute can take several. Excluding the C:/cmdstan directory from real-time scanning resolves it, where your organisation’s policy allows.

Compiling is blocked entirely. Some managed machines prevent newly compiled programs from running at all. This is a policy decision rather than a configuration problem and cannot be worked around from within R. Contact the organisers before the workshop rather than attempting a fix on the day.

TipTime box the native route

Give the steps above about thirty minutes. If the verification check passes, stop. If compilation fails for reasons of security policy rather than something you can configure, no further adjustment will resolve it; contact the organisers.

macOS

WarningUntested route

The organisers have no Mac available and have not tested these steps. They point to the upstream instructions, which are maintained by the projects themselves. Run the verification check when you have finished; passing it is what matters, not the route taken.

  1. Install R from CRAN, choosing the build for your processor. Apple Silicon and Intel builds differ.
  2. Install the Xcode Command Line Tools by running xcode-select --install in Terminal. Some packages also require gfortran; the CRAN macOS tools page describes the current requirement.
  3. Install Positron and Git.
  4. Install the R packages exactly as in the Windows section above.
  5. Follow the CmdStanR getting-started vignette for check_cmdstan_toolchain() and install_cmdstan(). The default installation path is not a problem on macOS, so dir need not be set.

Linux

Install R through your distribution’s package manager or from CRAN, and the standard build tools — build-essential on Debian and Ubuntu, or the equivalent development group on other distributions. Install Positron and Git. Then install the R packages as in the Windows section, and run check_cmdstan_toolchain() followed by install_cmdstan(). The default path is not a problem here either.

This route was verified on 2026-09-11 under Debian with R 4.6.1 and CmdStan 2.39.0.

The workshop materials

The modules, the example data and check_setup.R are in a public GitHub repository, https://github.com/open-AIMS/cr_modelling_training. Retrieve them before the workshop and put the folder somewhere you can find again. Avoid a folder that a cloud service synchronises while you work, such as OneDrive or Dropbox, because a synchronising folder can lock files while R is reading them.

Retrieval with Git

This is the route the Git installation above is for. Open a terminal — the Terminal pane in Positron, or Git Bash on Windows — change to the folder you want the materials in, and run:

git clone https://github.com/open-AIMS/cr_modelling_training.git

That creates a folder cr_modelling_training holding the whole course, including vignettes/check_setup.R.

The material is revised up to the workshop. On the morning, run

git pull

from inside that folder to take the current version. Taking revisions this way is the reason Git is on the list above; it has no other use during the day.

Retrieval without Git

If Git did not install, or your machine does not allow you to run it, download the materials as a ZIP file instead. Open https://github.com/open-AIMS/cr_modelling_training, select the green “Code” button, then “Download ZIP”, and extract the archive. You end up with the same folder. To take a later revision you download the ZIP again rather than running git pull.

The fitted models

The modules fit Bayesian models, and some of them take a while: on a four-core machine module 5 takes about thirteen minutes and module 6 about sixteen. You do not have to wait for that during the workshop. Every fit used in the material is available as a single download of about 42 MB, and with those objects in place each module loads its fits in seconds instead of sampling them.

Each module shows you the bnec() call that produced a fit, then the save() that kept it, then the load() that reads it back. The download supplies the saved objects, so the load() is what runs when you work through the page. That is the same sequence a real analysis follows, and it is why the fitting call stays visible rather than being hidden behind a cache.

From inside the cr_modelling_training folder, in R:

source("vignettes/fetch_fits.R")

That downloads the archive, checks it arrived complete, and unpacks it into a vignettes/fits/ folder beside the modules. It is done once. Do it on a connection you trust rather than on conference wifi on the morning.

The archive is revised while the material is being finished, so run git pull and then the line above again if you collected the materials more than a few days before the workshop. Re-running it replaces the saved fits in place.

NoteCopying the fits by hand

The same archive, cr_modelling_fits.zip, is on a USB stick on the day, and you can put the objects in place yourself without running anything. Copy it into your cr_modelling_training folder and extract it there. It holds the folders as well as the files, so the twenty-five .RData objects end up at:

cr_modelling_training/vignettes/fits/m2_bnec_fit.RData
cr_modelling_training/vignettes/fits/m4_bnec_fit.RData
...

The path matters, because each module runs with vignettes as its working directory and reads fits/ relative to that. A fits folder placed at the top level of cr_modelling_training is not found. Extract the archive at the top level of that folder and the path comes out right; extracting it inside vignettes gives vignettes/vignettes/fits, which is not found either.

The download is optional. Without it the material is complete and the modules are slower. Run the bnec() chunk each module shows, which is the one marked as not evaluated, followed by its save() line. That writes the same file into fits/, and the load() below it then works exactly as it does for everyone else.

The verification check below reports whether the fitted models are present, so you do not have to work it out yourself.

Opening the materials in Positron

Use “File > Open Folder” and select the cr_modelling_training folder. R then starts in that folder, so a relative path such as source("vignettes/check_setup.R") resolves without you typing a full path.

The verification check

check_setup.R is supplied alongside this document, in the vignettes/ folder of the materials you retrieved in the previous section. It installs nothing. It reports what you have, compiles and fits a small model, and finishes with either READY or NOT READY.

The most reliable way to run it is to open check_setup.R itself in Positron (not just this document) and run the whole file from there — for example with Positron’s “Source” button, or by selecting all the code and running it. Positron then runs it from the folder the file is saved in, which avoids the error below.

If you instead want to run it from the R console with source(), R needs to be told where the file is. Pasting

source("check_setup.R", echo = FALSE)

only works if your R console’s working directory is already the vignettes/ folder — otherwise you will see:

Warning message:
In file(filename, "r", encoding = encoding) :
  cannot open file 'check_setup.R': No such file or directory
Error in `file()`:
! cannot open the connection

This is not a sign of a broken installation; it means R was looking in the wrong folder. Either open check_setup.R in Positron and run it from there (the first option above), or give source() the full path to the file, for example:

source("C:/path/to/cr_modelling_training/vignettes/check_setup.R", echo = FALSE)

replacing the path with wherever you saved the workshop materials.

Every run takes a few minutes, because it compiles a model each time rather than reusing an earlier build. That is deliberate: reusing a build would let the check pass without ever invoking the compiler, which is the thing being tested.

A successful run ends like this:

Summary
-------
READY. Every check passed.

A warning rather than a failure means you can follow the workshop but something is not as expected — a home directory the CmdStan build cannot use, or a cmdstanr too old for the Rtools these instructions specify. Read the warning and act on it if you can.
